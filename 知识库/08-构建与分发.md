# 08 构建与分发

## 一、酒馆助手脚本的导入格式

用户导入酒馆助手的"脚本"是一个 JSON 文件：

```json
{
  "type": "script",
  "enabled": true,
  "name": "角色名注入 v1.0.0",
  "id": "f65ab164-4268-4366-8228-16af904c2251",
  "content": "(() => { 'use strict'; /* 全部 JS 代码 */ })();",
  "info": "角色名注入：悬浮窗管理角色名条目，点击注入输入框并定位光标。\n入口：酒馆助手脚本按钮「角色名注入」。",
  "button": {
    "enabled": true,
    "buttons": [{ "name": "角色名注入", "visible": true }]
  },
  "data": {},
  "export_with": { "data": true, "button": true }
}
```

要点：

- `content` 是**整段 JS 源码字符串**，会被酒馆助手当作脚本内容执行。
- `id` 必须是 UUID；每次重新生成会让用户导入后变成一个新脚本（更新时最好保留原 id）。
- `button.buttons` 声明按钮；脚本内再用 `appendInexistentScriptButtons` 兜底补上（用户删了按钮也能自动加回来）。
- `info` 是作者注释，显示在脚本编辑界面。
- `export_with.data` / `export_with.button` 控制导出时是否带上脚本变量与按钮配置。

## 二、构建流程（推荐照抄本地项目的做法）

`制作-角色生成加入世界书` 项目的方案：源码单文件 + 一个几十行的构建脚本。

```
项目/
├── 角色名注入.js              # 源码（唯一的开发入口，单文件 IIFE）
├── build.js                   # 构建：读源码 → 输出可导入的 JSON
├── 角色名注入-v1.0.0.json      # 构建产物：导入酒馆用
└── 角色名注入-v1.0.0.full.js   # 构建产物：完整 JS（便于测试切片）
```

`build.js` 骨架：

```javascript
const fs = require('fs');
const crypto = require('crypto');

const version = '1.0.0';
const src = fs.readFileSync('角色名注入.js', 'utf8');

const out = {
  type: 'script',
  enabled: true,
  name: `角色名注入 v${version}`,
  id: crypto.randomUUID(),
  content: src,
  info: [
    '角色名注入：悬浮窗管理"角色名-描述-预设消息"条目，点击条目注入输入框并定位光标。',
    '入口：酒馆助手脚本按钮「角色名注入」。',
    `版本：${version}`,
  ].join('\n'),
  button: { enabled: true, buttons: [{ name: '角色名注入', visible: true }] },
  data: {},
  export_with: { data: true, button: true },
};

fs.writeFileSync(`角色名注入-v${version}.json`, JSON.stringify(out, null, 2), 'utf8');
fs.writeFileSync(`角色名注入-v${version}.full.js`, src, 'utf8');
console.log(`已构建 v${version}`);
```

版本号只维护在一处（源码里的 `const SCRIPT_VERSION`），构建脚本读它自动生成文件名。

## 三、开发期热更新

### 方式 1：手动复制（最简单，零配置）

改源码 → 运行 `node build.js` → 打开酒馆助手脚本库 → 编辑脚本 → 全选粘贴新代码 → 保存。

适合单文件、改动不频繁的情况。

### 方式 2：本地服务器 + 远程 import（模板方案）

模板 `tavern_helper_template-main` 的做法：`pnpm watch` 起 webpack watch，产物推到 `localhost:5500`，酒馆里放一个加载器脚本：

```json
{
  "name": "脚本-实时修改",
  "content": "import 'http://localhost:5500/dist/角色名注入/index.js'"
}
```

代码一改，刷新酒馆就是新的。**代价**：需要装 pnpm + webpack 全家桶，且要求酒馆能访问 localhost。

### 方式 3：Chrome DevTools MCP + 实时监听

模板支持通过 chrome-devtools MCP 连接已打开的浏览器里的酒馆页面，检查"酒馆助手-实时监听-允许监听"开关，开启后代码变更热重载，无需刷新页面。适合重度开发。

**本项目建议**：先用方式 1（单文件，改动就是复制粘贴），需要频繁迭代时再上方式 2。

## 四、测试

单文件 IIFE 也可以有测试。本地项目的做法是从构建产物里切片出纯函数再断言：

```javascript
// test-parser.js 思路
const full = fs.readFileSync('角色名注入-v1.0.0.full.js', 'utf8');
// 用标记切片出纯函数区段
const code = full.split('/* __TEST_SLICE_START__ */')[1].split('/* __TEST_SLICE_END__ */')[0];
eval(code);
// 断言
console.assert(injectText('徐渭：“|”').cursor === 4);
```

**推荐做法**：把纯逻辑（光标下标计算、模板解析、数据迁移）写成不依赖 DOM 的纯函数，用标记包裹，测试脚本切片后 `eval` 断言。这样无需构建工具也能保证核心逻辑正确。

## 五、分发

### 本地文件

把 `角色名注入-v1.0.0.json` 发给朋友，在酒馆助手 → 脚本库 → 导入。

### jsdelivr（GitHub 仓库）

推到 GitHub 后，用 jsdelivr CDN 地址作为脚本内容：

```javascript
import 'https://testingcf.jsdelivr.net/gh/用户名/仓库名@版本/dist/角色名注入/index.js'
```

好处：更新后用户不用手动重导。注意 jsdelivr 有缓存，配合版本号或 tag 使用。

**官方注意事项：避免使用国外 CDN**（部分用户网络环境访问困难），国内可用 `gcore.jsdelivr.net` 或直接分发 JSON 文件。

## 六、更新时的数据兼容

用户已经存了条目数据，新版本改了结构必须能读旧数据：

```javascript
function migrate(data) {
  const v = data.version || 0;
  if (v < 1) { /* 0 → 1 的字段改名等 */ data.version = 1; }
  return data;
}
```

### 脚本 id 怎么处理

`id` 决定"导入这份 JSON 会不会变成一个新脚本"。两种策略：

| 策略 | 效果 | 什么时候用 |
| --- | --- | --- |
| **id 固定** | 导入新版本时不容易变成两个脚本 | 数据存在**脚本变量**里（`{type:'script'}`）——那些数据是按 script_id 索引的，换 id 就读不到了 |
| **id 跟着名称走** | 每次发版都是全新脚本，用户需手动停用旧版 | 数据**不挂在脚本 id 上**（存在全局变量、角色卡变量里） |

本项目用的是第二种：`build.js` 把「名称 + id」存进 `.script-id`，名称变了就生成新 id，
名称没变时重复构建复用同一个 id。因为条目存在全局变量和角色卡变量里，换 id 不丢数据。

**配套要做的**：如果两个版本同时启用（用户忘了停用旧的），
`uninstall()` 里必须判断实例令牌是否已被接管，被接管就不要删 DOM，
否则用户停用旧版本时会把新版本的界面一起抹掉：

```javascript
function uninstall() {
  clearBallListeners();
  clearPageListeners();
  // 令牌已被更新的版本接管时不要动 DOM——那已经是别人的界面了
  if (host[INSTANCE_KEY] === TOKEN) {
    removeOwnNodes();
    delete host[INSTANCE_KEY];
  }
  closeModal();
}
```
